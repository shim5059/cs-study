## 1. 속성/투플(대상) vs 차수/카디널리티(개수)

### 처음 생각 (오답)
속성·투플과 차수·카디널리티를 같은 말로 섞어 썼다. 카디널리티를 계산할 때는 **머리줄(속성 이름 줄)**까지 개수에 넣었다 빼는 식으로 헷갈렸다.

### 원리
```
         ┌────── 속성(열) 하나하나 ─────┐
         ▼          ▼         ▼
       고객아이디 | 고객이름 | 나이        ← 머리줄 = 스키마 (투플 아님)
       ─────────┼─────────┼─────
투플 ▶  cat      | 김민준   | 23
투플 ▶  dog      | 이서연   | 31

차수       = 속성 "개수" = 3
카디널리티  = 투플 "개수" = 2  (머리줄은 셀 대상이 아님)
```
투플 5개 + 3개 삽입 − 1개 삭제 → 카디널리티 = 5 + 3 − 1 = 7. 머리줄은 처음부터 개수에 없으니 따로 뺄 필요가 없다.

### 깨달음
속성·투플은 **대상**(열 하나, 행 하나), 차수·카디널리티는 그것의 **개수**. "차수=열 개수, 카디널리티=행 개수, 머리줄 제외".

## 2. 도메인 = 속성이 가질 수 있는 "모든 값의 집합"

### 처음 생각 (오답)
도메인을 **투플**이나 "**열 자체**"로 착각했다.

### 원리
```
나이 속성의 도메인 = { 0, 1, 2, … , 150 }   ← 가질 "수 있는" 값 전체
실제 들어 있는 값  = { 23, 31, NULL }       ← 인스턴스
```
열(속성)은 이름이 붙은 칸이고, 도메인은 그 칸에 들어갈 **수 있는** 값의 범위다.

### 깨달음
도메인 = **가능한 값의 집합**. 자료형(`INT`, `VARCHAR(20)`)과 `CHECK` 조건이 이 범위를 정한다.

## 3. 투플의 유일성 서술

### 처음 생각 (오답)
"투플이 **하나만** 있어야 한다"고 썼다.

### 원리
```
 cat | 김민준 | 23
 dog | 이서연 | 31     ← 투플 여러 개 OK
 cat | 김민준 | 23     ← 완전히 같은 투플이 또 있음 ✗
```

### 깨달음
교재 문장 그대로: "하나의 릴레이션에는 **동일한 투플이 존재할 수 없다**".

## 4. 슈퍼키 vs 후보키 (최소성)

### 처음 생각 (오답)
- `{학번, 이름}`을 **후보키**로 골랐다.
- 이름을 후보키로 생각했다.
- 서술할 때 유일성·최소성의 **뜻**과 포함 관계를 쓰지 않았다.

### 원리
```
{학번, 이름}
  유일성: 학번이 이미 다 달라서 구별 가능 ○
  최소성: 이름을 빼도 {학번}만으로 구별됨 → 이름은 불필요 ✗
  ⇒ 슈퍼키 ○, 후보키 ✗

{이름}
  유일성: 동명이인이 있으면 구별 불가 ✗  ⇒ 키가 될 수 없음
```
```
슈퍼키(유일성)  ⊃  후보키(유일성+최소성)  ⊃  기본키(후보키 중 선택)
```

### 깨달음
"하나 빼 봐도 여전히 구별되나?" → 된다면 최소성 위반, **슈퍼키까지만**.

## 5. 외래키는 NULL 가능, 이름 달라도 됨

### 처음 생각 (오답)
외래키도 기본키처럼 **NULL이 불가능**하고, 참조하는 기본키와 **이름이 같아야** 한다고 생각했다.

### 원리
```
 주문(주문번호, 주문고객, …)          고객(고객아이디, …)
             └──── 외래키 ──참조──▶ 기본키
              이름 다름 OK            도메인(VARCHAR(20))만 같으면 됨

 주문 o9의 주문고객 = NULL   → "아직 고객이 정해지지 않음" → 허용
 주문 o1, o3의 주문고객 = cat → 같은 고객이 여러 번 주문 → 중복 허용
```
`FOREIGN KEY` + `PRIMARY KEY`가 둘 다 걸린 열이 아니라면, 외래키는 NULL·중복이 모두 가능하다. (7주차 SQL로 `주문고객`에 NULL 삽입이 성공하는 것도 확인)

### 깨달음
NULL 금지는 **기본키(개체 무결성)** 규칙이지 외래키 규칙이 아니다.

## 6. 참조 방향을 거꾸로 읽음

### 처음 생각 (오답)
- "학과번호가 학생을 참조한다"고 썼다.
- 외래키에 NULL을 넣는 것을 **참조 무결성 위반**으로 골랐다. (오답노트 재시험에서도 **다시** 틀림)
- 없는 학과 `D9`로 학생을 삽입하는 것을 **문제없는 연산**으로 골랐다.

### 원리
```
  학생                               학과
 ┌─────┬──────┬────────┐          ┌────────┬────────┐
 │ 학번 │ 이름  │ 학과번호 │ ──참조──▶ │ 학과번호 │ 학과명  │
 ├─────┼──────┼────────┤          ├────────┼────────┤
 │ s01 │ 가람  │ D1     │ ───────▶ │ D1     │ 컴퓨터  │  ✓ 있는 값
 │ s02 │ 나래  │ NULL   │          │ D2     │ 경영    │  ✓ 아직 미정 (위반 아님)
 │ s03 │ 다온  │ D9     │ ───────▶ │  ???   │        │  ✗ 없는 값 → 거부
 └─────┴──────┴────────┘          └────────┴────────┘
   자식 (외래키 쪽)                    부모 (기본키 쪽)
```
화살표는 **외래키를 가진 쪽 → 기본키 쪽**으로만 그린다. 참조 무결성이 막는 것은 "**없는 값**을 가리키는 것"이고, NULL은 아무것도 가리키지 않으니 위반이 아니다.

### 깨달음
- 외래키를 가진 쪽(학생)이 **참조하는** 쪽
- 위반 = "존재하지 않는 값을 가리킴". NULL ≠ 위반, 없는 값(D9) = 위반

---

## 7. 참조 무결성 때문에 거부되는 연산 구분

### 처음 생각 (오답)
어느 릴레이션의 어떤 연산이 거부될 수 있는지 구분하지 못했다.

### 원리
```
                 위험한 연산
 학생 (참조하는 쪽)  삽입, 외래키 수정   → 없는 학과를 가리키게 될 수 있음
 학과 (참조되는 쪽)  삭제, 기본키 수정   → 학생이 가리키던 학과가 사라질 수 있음
```
반대로 학과에 **새 학과를 삽입**하거나 학생을 **삭제**하는 건 아무도 잃는 참조가 없어서 안전하다.

### 깨달음
"이 연산 뒤에 **허공을 가리키는 외래키**가 생기나?"만 확인하면 된다.

## 8. 무결성 이름과 정의 문장

### 처음 생각 (오답)
- 개체 무결성을 "**키 무결성**"이라고 불렀다.
- 서술형에서 교재 정의 문장 대신 풀이말을 썼다.

### 원리

| 이름 | 정의 문장 (그대로 외움) |
|---|---|
| **개체** 무결성 | 기본키를 구성하는 모든 속성은 널 값을 가질 수 없다 |
| **참조** 무결성 | 외래키는 참조할 수 없는 값을 가질 수 없다 |

"**모든** 속성"인 이유: 기본키가 `{주문번호, 상품번호}`처럼 여러 속성이면 그중 **하나라도** NULL이면 안 된다.

### 깨달음
이름은 **개체/참조**, 문장은 교재 그대로. 교수님 강조 "본인의 언어로" 쓰더라도 핵심 문장은 빠뜨리지 않는다.

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| 속성/투플 = 차수/카디널리티 | 앞은 **대상**, 뒤는 **개수** |
| 머리줄도 카디널리티 계산에 넣음 | 머리줄은 투플이 아님 |
| 도메인 = 투플/열 | 속성이 가질 수 있는 **모든 값의 집합** |
| 투플이 하나만 | **동일한** 투플이 존재할 수 없음 |
| {학번, 이름} = 후보키 | 최소성 ✗ → **슈퍼키** |
| 외래키 NULL 불가, 이름 같아야 함 | **NULL·중복 가능**, 이름 달라도 도메인만 같으면 됨 |
| 학과번호가 학생을 참조 | **외래키 쪽 → 기본키 쪽** (학생 → 학과) |
| 외래키 NULL = 참조 무결성 위반 | NULL은 위반 아님, **없는 값**이 위반 |
| 거부 연산 구분 못 함 | 자식: 삽입·FK 수정 / 부모: 삭제·PK 수정 |
| 키 무결성 | **개체** 무결성 |
