## 1. 관계 대수 vs 관계 해석

| | 관계 대수 | 관계 해석 |
|---|---|---|
| 방식 | **절차적** (어떻게 구할지 순서대로) | **비절차적** (무엇을 원하는지만) |
| 기반 | 연산자 | **프레디킷 해석**(수학의 논리) |
| 표현 능력 | 동등 | 동등 |

- **폐쇄 특성**: 연산의 피연산자도 릴레이션, **결과도 릴레이션** → 결과를 또 다른 연산에 넣을 수 있음
- **관계적으로 완전**: 관계 대수로 표현할 수 있는 모든 질의를 표현할 수 있는 질의 언어 (SQL이 그렇다)

## 2. 연산자 8가지

| 분류 | 연산자 | 기호 | 결과 |
|---|---|---|---|
| 일반 집합 | 합집합 | ∪ | 둘 중 하나라도 있는 투플 (중복 1번) |
| | 교집합 | ∩ | 둘 다 있는 투플 |
| | 차집합 | − | R에는 있고 S에는 없는 투플 |
| | 카티션 프로덕트 | × | 모든 투플의 조합 |
| 순수 관계 | 셀렉트 | σ | 조건을 만족하는 **투플(행)** |
| | 프로젝트 | π | 원하는 **속성(열)**만, 중복 제거 |
| | 조인 | ⋈ | 공통 속성으로 이어 붙임 |
| | 디비전 | ÷ | S의 **모든** 값과 관련 있는 R의 투플 (S 속성은 빼고) |

- ∪ ∩ −는 **합병 가능**해야 함: 차수가 같고, 대응하는 속성의 도메인이 같음
- **교환적 특징**: ∪ ∩ × ⋈는 순서를 바꿔도 같음, **−만 교환 안 됨** (R − S ≠ S − R)

## 3. 차수 · 카디널리티 계산

R(차수 r, 카디 a), S(차수 s, 카디 b)

| 연산 | 차수 | 카디널리티 |
|---|---|---|
| R ∪ S | r | max(a, b) ~ a + b |
| R ∩ S | r | 0 ~ min(a, b) |
| R − S | r | 0 ~ a |
| R × S | **r + s** (더하기) | **a × b** (곱하기) |
| σ(R) | r (그대로) | 0 ~ a (줄 수 있음) |
| π(R) | 지정한 속성 수 | 1 ~ a (중복 제거로 줄 수 있음) |
| R ⋈N S (공통 속성 k개) | r + s − k | 조인 조건에 따라 |
| R ⋉ S | **r** (R 속성만) | 0 ~ a |

예: 고객(차수 3, 카디 5) × 주문(차수 3, 카디 6) → 차수 **6**, 카디널리티 **30** (sqlite로 확인)

## 4. 표기법 (이 저장소에서 쓰는 대괄호 표기)

```
σ[조건](릴레이션)          σ[등급 = 'gold'](고객)
π[속성 리스트](릴레이션)     π[고객이름](고객)
∧ = 그리고(AND), ∨ = 또는(OR), ¬ = 아님(NOT)
```

## 5. 조인 종류

| 조인 | 결과 |
|---|---|
| 세타 조인 (⋈θ) | 조건에 비교 연산자(= ≠ < > ≤ ≥) 사용 |
| 동등 조인 | 세타 조인 중 비교 연산자가 **=**, 조인 속성이 결과에 **두 번** 나옴 |
| 자연 조인 (⋈N, N = **Natural**) | 동등 조인 결과에서 **중복된 조인 속성을 하나 제거** |
| 세미 조인 (⋉) | 자연 조인 후 **왼쪽(R) 릴레이션의 속성만** 남김 |
| 외부 조인 (⋈+) | 조인에 **실패한 투플도** 버리지 않고 상대 속성을 **NULL**로 채워 포함 |

직접 만든 예 (sqlite로 확인): 고객(고객아이디, 고객이름, 등급) 5명, 주문(주문번호, 고객아이디, 수량) 6건, 주문 없는 고객 2명

| 연산 | 차수 | 카디널리티 |
|---|---|---|
| 고객 ⋈N 주문 | 3 + 3 − 1 = 5 | 6 |
| 고객 ⋉ 주문 | 3 | 3 (주문한 고객만) |
| 고객 왼쪽 외부 조인 주문 | 5 | 8 (6 + 주문 없는 고객 2) |

## 7. 문장 → 관계 대수식 순서

> "수량 15개 이상을 주문한 고객의 고객이름을 검색하라"

결과 속성(고객이름)은 고객에, 조건 속성(수량)은 주문에 있다 → **조인이 필요**
```
① 조인       고객 ⋈N 주문
② 셀렉트     σ[수량 ≥ 15](고객 ⋈N 주문)
③ 프로젝트   π[고객이름](σ[수량 ≥ 15](고객 ⋈N 주문))
```
결과: 이서연, 김하은 (sqlite로 확인)

## 8. 데이터베이스 설계 5단계 (8장)

| 단계 | 하는 일 | 결과물 |
|---|---|---|
| 1. 요구사항 분석 | 사용자 요구 수집·분석 | 요구사항 명세서 |
| 2. 개념적 설계 | **DBMS에 독립적인** 개념적 구조 설계 | E-R 다이어그램 (개념적 스키마) |
| 3. 논리적 설계 | DBMS에 맞는 논리적 구조로 변환 | **논리적 스키마 (릴레이션 스키마)** |
| 4. 물리적 설계 | 저장 장치에 맞는 물리적 구조 (저장 구조, 인덱스) | 물리적 스키마 |
| 5. 구현 | SQL **DDL을 실행**해 DB 생성 | 실제 DB |

## 9. ERD → 릴레이션 변환 규칙

| 규칙 | ERD | 릴레이션 |
|---|---|---|
| 1. 모든 개체 → 릴레이션 | `[학생]` 학번, 이름 | `학생(학번, 이름)` |
| 복합 속성 | 주소{시, 구} | 열을 **쪼갬**: `회원(…, 시, 구)` |
| 2. N:M 관계 → 릴레이션 | 학생 N─<수강>─M 과목, 성적 | `수강(학번, 과목번호, 성적)` — **양쪽 기본키**를 외래키로 + **관계 속성**, 기본키는 (학번, 과목번호) |
| 3. 1:N 관계 → 외래키 | 부서 1─<소속>─N 사원 | **N 쪽**에 1 쪽 기본키: `사원(사원번호, …, 부서번호)` |
| 약한 개체 | 사원═<<부양>>═[[부양가족]] | `부양가족(사원번호, 이름, 관계)` 기본키 = **주인 키 + 부분키** |
| 4. 1:1 관계 → 외래키 | 사원 1─<배정>─1 사물함 (사물함 필수) | **필수 참여 쪽**에 외래키: `사물함(사물함번호, 사원번호)`, 양쪽 다 필수면 **하나로 합침** |
| 5. 다중 값 속성 → 릴레이션 | 회원의 ((전화번호)) | `회원전화번호(회원번호, 전화번호)` 독립 릴레이션 |
| 순환 관계 (1:N) | 사원이 사원을 멘토링 | 같은 릴레이션에 자기 참조 외래키: `사원(사원번호, 이름, 멘토사원번호)` |

- 1:1, 1:N 관계도 릴레이션으로 만들 수는 있다 (기타 고려 사항). 기본은 외래키
