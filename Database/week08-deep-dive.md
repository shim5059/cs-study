## 1. 격리성: "무엇을 막나" + "왜 막나"

### 처음 생각 (오답)
> "먼저 수행하던 계좌이체가 끝날 때까지 다른 곳에서는 정보를 간섭할 수 없음"

무엇을 막는지는 맞았지만, **왜** 막아야 하는지(모순 방지)를 쓰지 않았다.

### 원리
```
계좌이체 T1:  A에서 3000 출금 ──────────(중간 상태)────────── B에 3000 입금 → commit
                  A 7000, B 5000  ← 돈 3000이 "공중에 떠 있음"
                        ▲
조회 T2:        이때 A+B 합계를 읽으면 12000 (원래 15000) → 모순된 값
```
격리성이 없으면 다른 트랜잭션이 **완료되지 않은 중간 결과**를 읽고 그 위에 작업해서, 실제로는 존재한 적 없는 상태를 보게 된다.

### 깨달음
격리성 서술 = **① 수행 중인 트랜잭션의 중간 결과에 다른 트랜잭션이 접근 못 함** + **② 모순된 데이터 접근을 막기 위해**. 두 개를 다 써야 완성.

## 2. 트랜잭션 상태: 실패는 "언제든", 완료는 "부분 완료를 거쳐서만"

### 처음 생각 (오답)
> "트랜잭션 중간에 문제의 유무 차이로 부분 완료와 실패로 갈림 / 둘 다 성공하거나 둘 다 안한걸로 쳐야하기 때문에(원자성)"

갈리는 결과만 말했고, 질문이 원한 **비대칭**(왜 완료만 중간 단계를 거치는지)은 답하지 못했다. 원자성은 핵심 논점이 아니었다.

### 원리
```
 [활동] ── 연산1 ── 연산2 ── 연산3(마지막) ──▶ [부분 완료] ── commit ──▶ [완료]
    │        │        │                          │
    └────────┴────────┴──── 장애는 아무 때나 ──────┴──▶ [실패] ── rollback ──▶ [철회]
```
- 장애는 **어느 연산 도중에든** 날 수 있으니, 활동 상태에서 바로 실패로 빠질 수 있다
- 완료는 **모든 연산이 끝나야** 가능하니, 반드시 "마지막 연산이 끝난 직후" = **부분 완료**를 거친다
- 부분 완료에서도 commit 전에 장애가 나면 실패로 갈 수 있다

### 깨달음
**실패 = 언제든, 완료 = 모든 연산 종료 후에만**. 이 비대칭 때문에 성공 쪽에만 부분 완료라는 중간 단계가 있다.

## 3. 체크포인트 이후 시작해 끝나지 못한 트랜잭션은 왜 undo?

### 처음 생각 (오답)
> "undo 해야함, 장애 시점까지 완료되지 않은거면 / 장애 시점의 데이터가 손실되었을 수 있기 때문에"

결론(undo)은 맞았지만 이유를 **데이터 손실**로 잘못 짚었다.

### 원리
```
             검사 시점                     장애
 ─────────────────┼──────────────────────────┼──▶
 T5               │   ━━━ write ━━━ write ━━━┥  (commit 못 함)
                  │        ▼        ▼
                  │   즉시 갱신: DB에 이미 반영됨
                  │
 장애 후 DB:  T5가 "반쯤" 바꿔 놓은 값이 남아 있음 → 원자성 위반
 해결:        로그의 변경 "전" 값으로 되돌림 = undo
```
문제는 데이터가 **사라진 것**이 아니라, 완료되지 않은 변경이 **남아 있는 것**이다.
지연 갱신이었다면 commit 전에는 DB에 아무것도 반영하지 않으므로 undo할 것도 없다.

### 깨달음
undo 이유 = **미완료 트랜잭션이 이미 반영한 변경분을 지워야 해서**. redo는 반대로 "commit 됐는데 디스크에 반영이 안 됐을 수 있어서".

## 4. 2단계 로킹이 막는 것은 교착 상태가 아니다

### 처음 생각 (오답)
> "확장 단계에서 lock으로 미리 다 필요한 것들을 잠구고 시작해야함, unlock 시 교착상태에 빠질 수 있기 때문에 → 교착상태가 진행되면 무한 대기하는 것이기 때문에 비직렬 스케줄이 됨"

2단계 로킹과 교착 상태를 원인과 결과로 엮었다.

### 원리
```
lock을 일찍 풀면 (2PL 위반)
 T1: lock(A) write(A) unlock(A)                    lock(B) write(B) …
 T2:                            lock(A) read(A) …  ← T1이 아직 안 끝났는데 A를 가져감
                                → 순서대로 실행했을 때와 다른 결과 = 직렬 가능성 깨짐

2PL을 지켜도
 T1: lock(A) ───── lock(B) 기다림 ─┐
 T2: lock(B) ───── lock(A) 기다림 ◀┘   → 교착 상태는 그대로 생길 수 있음
```

| | 2단계 로킹 | 교착 상태 |
|---|---|---|
| 정체 | 해결책 | 문제 |
| 하는 일 | lock 거는 단계와 푸는 단계를 나눠 **직렬 가능성 보장** | 서로의 lock을 기다리며 무한 대기 |
| 관계 | 2PL을 쓰면 오히려 **생길 수 있음** | 예방·회피·탐지 후 회복으로 따로 해결 |

### 깨달음
2PL이 막는 것 = **lock을 일찍 풀어서 생기는 모순된 데이터 접근(직렬 가능성 깨짐)**. 교착 상태는 2PL의 **부작용**이지 2PL이 막는 대상이 아니다.

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| 격리성 = 간섭 금지만 서술 | 중간 결과 접근 차단 + **모순 방지** 이유까지 |
| 상태 분기를 "문제 유무"·원자성으로 설명 | 실패는 **언제든**, 완료는 **부분 완료를 거쳐서만** |
| 미완료 트랜잭션 undo 이유 = 데이터 손실 | 이미 반영된 **미완료 변경분을 취소**하려고 |
| 2PL = 교착 상태 방지 | 2PL = **직렬 가능성 보장**, 교착 상태는 그 부작용 |
