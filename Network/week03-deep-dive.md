## 1. DNS 캐시가 라우팅·MAC 주소 변환까지 생략해 준다는 착각

### 처음 생각 (오답)
한 번 통신해서 DNS 캐시가 저장되면, 두 번째 통신부터는 IP를 가지고 라우터와 MAC 주소를 타고 찾아가는 작업까지 생략되어 속도가 빨라지는 것이라고 생각했다.

### 원리
```text
[1단계: 이름 → IP 조회]  www.naver.com ──(DNS)──→ 223.130.200.236
                         ★ DNS 캐시는 오직 이 1단계만 생략해 준다!

[2단계: 실제 패킷 전송]  내 PC → 게이트웨이 → 라우터 A → 라우터 B → 네이버 서버
                         ★ 서브넷 판단, 라우팅, 구간별 MAC 교체는 패킷을 보낼 때마다 매번 일어난다!
```
또한 같은 동네(LAN) 안에서 IP로 MAC을 물어보는 과정을 줄여주는 것은 DNS 캐시가 아니라 **ARP 캐시**(`arp -a`)다.

### 깨달음
**DNS 캐시는 "도메인 → IP 번호판 알아내기"만 줄여줄 뿐**, 알아낸 주소로 택배(패킷)를 배송하는 라우팅·MAC 교체 과정은 매번 똑같이 진행된다.

## 2. DNS 레코드 `A` / `AAAA` 자리에 비트 수를 적음

### 처음 생각 (오답)
- "IPv4 주소 / IPv6 주소를 나타내는 DNS 레코드 이름은?"이라는 질문에 `32비트 / 128비트`라고 답했다.
- 또 다른 연습문제에서는 `A = 기본 도메인`, `AAAA = 권한 DNS`라고 답했다.

### 원리
`32비트 / 128비트`는 IPv4와 IPv6의 **주소 길이**고, DNS 장부에 적힌 **레코드(항목) 이름**은 따로 있다.

```text
A     (Address)       → 도메인을 32비트 IPv4 주소로 매핑
AAAA  (Quad A)        → 도메인을 4배 긴 128비트 IPv6 주소로 매핑 (4배 길어서 A가 4개)
NS    (Name Server)   → 그 도메인의 권한 DNS 서버를 지정
```

### 깨달음
질문이 "몇 비트인가?"인지 "무슨 레코드인가?"인지 끝 단어를 확인한다. 권한 DNS를 가리키는 레코드는 `AAAA`가 아니라 **`NS`** 다.

## 3. HTTP 응답 시작줄 조각 나누기와 POST의 보안성

### 처음 생각 (오답)
- `HTTP/1.1 404 Not Found`를 세 조각으로 나눌 때 `HTTP = 스킴`, `1.1 = 모름`, `404 Not Found = 응답 정보`로 묶었다.
- POST 방식이 안전하지 않은 이유를 "개발자 도구(F12)로 보면 보이기 때문"이라고 적었다.

### 원리
1. **시작줄 구조**: 스킴(`http://`)은 URL의 맨 앞 부분이고, 응답 메시지의 첫 줄은 띄어쓰기 기준으로 이렇게 나뉜다.
   ```text
   HTTP/1.1        404           Not Found
   └──────┘      └─────┘         └───────┘
   HTTP 버전     상태 코드(숫자)   설명 문구(사람용)
   ```
2. **POST와 암호화**: 브라우저 개발자 도구는 **내 컴퓨터 화면**이므로 HTTPS로 암호화를 해도 당연히 보인다. 평문 `http://`에서 POST가 위험한 진짜 이유는, 본문에 넣어도 **암호화가 안 되어 중간 네트워크 경로에서 Wireshark 같은 패킷 스니핑 도구로 엿볼 수 있기 때문**이다.

### 깨달음
응답 시작줄은 **버전 · 상태 코드 · 설명** 세 조각이고, POST가 `http://`에서 위험한 이유는 개발자 도구가 아니라 **평문 전송이라 중간 경로에서 도청(Wireshark 캡처)이 가능하기 때문**이다.

## 4. 상태 코드 `301` · `302` · `304`와 `401` vs `403` 혼동

### 처음 생각 (오답)
- `2xx = 전송 중`, `3xx = 서버 잘못`, `500 = 리다이렉션`으로 앞자리 의미를 섞어 적었다.
- `301, 302, 304`를 모두 "접근 권한 없음"이라고 적었다.
- `401 = 클라이언트 잘못`, `403 = 서버 잘못`이라고 답했다.

### 원리
앞자리 숫자가 큰 분류를 결정한다: **2xx 성공 / 3xx 리다이렉션(이동·캐시) / 4xx 클라이언트 오류 / 5xx 서버 오류**.

```text
[3xx 리다이렉션·캐시]
301 Moved Permanently : 영구 이동 ("저희 아예 이사했어요")
302 Found             : 임시 이동 ("오늘만 옆 가게로 오세요")
304 Not Modified      : 변경 없음 ("갖고 계신 캐시 사본 그대로 쓰세요" → 본문 없음)

[4xx 클라이언트 오류 중 출입 거부 2종]
401 Unauthorized      : 인증(Authentication) 안 됨 → "신분증 보여주세요(누군지 모름, 로그인 필요)"
403 Forbidden         : 권한(Authorization) 없음   → "누군지는 아는데 VIP룸 출입 권한이 없어요"
```

### 깨달음
`401`과 `403`은 둘 다 `4xx`(클라이언트 쪽 오류)이며, 차이는 **"누군지 아직 모름(401 인증 필요)" vs "누군지 알지만 권한 없음(403 접근 금지)"** 이다.

## 5. 웹페이지 추가 요청 리소스에 `쿠키, 캐시, 세션`을 적음

### 처음 생각 (오답)
"브라우저가 하나의 웹 페이지를 표시할 때 추가로 요청할 수 있는 리소스 3가지"를 묻는 문제에 `쿠키, 캐시, 세션`이라고 답했다.

### 원리
쿠키·캐시·세션은 데이터 저장·상태 관리 메커니즘이지, 웹 페이지를 그리기 위해 서버에 `GET`으로 요청하는 **파일(리소스)** 이 아니다.
브라우저는 최초에 `HTML` 문서를 받은 뒤, 그 안에 적힌 태그(`<img src=...>`, `<link href=...>`, `<script src=...>`)를 보고 **이미지, CSS 스타일시트, JavaScript 파일**(또는 웹 폰트, 영상)을 추가로 요청한다.

### 깨달음
웹 페이지를 구성하는 추가 요청 리소스 3총사는 **이미지 · CSS · JavaScript**다.

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| DNS 캐시가 라우팅·MAC 변환도 생략함 | DNS 캐시는 도메인→IP 조회만 생략, 패킷 라우팅은 매번 진행 |
| IPv4/IPv6 레코드 = 32비트/128비트 | 레코드 이름은 `A`(IPv4)와 `AAAA`(IPv6) |
| POST는 개발자 도구에 보여서 위험함 | 평문(`http`)이라 중간 경로에서 Wireshark로 스니핑되어 위험함 |
| 301·302·304 = 권한 없음 / 403 = 서버 오류 | 301 영구이동·302 임시이동·304 캐시사용 / 401 미인증·403 권한없음 |
| 추가 요청 리소스 = 쿠키·캐시·세션 | 추가 요청 리소스 = 이미지 · CSS · JavaScript |
