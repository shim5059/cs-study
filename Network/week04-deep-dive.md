## 1. 인증서의 증명 방향을 4번 연속 반대로 적음

### 처음 생각 (오답)
TLS에서 인증서(Certificate)의 역할을 쓸 때 "서버에서 사용자를 신뢰하기 위한 보안 장치", "사용자의 브라우저가 기관·서버에게 본인임을 증명하는 것"이라고 **주체와 대상을 정반대로** 적었다.

### 원리
우리가 인터넷뱅킹이나 쇼핑몰에 접속할 때, 손님(브라우저)이 신분증을 내미는 것이 아니라 **은행 창구 직원(서버)이 "저희는 가짜 피싱 사이트가 아니라 진짜 은행 서버입니다"라고 사원증(인증서)을 보여주는 것**이다.

```text
서버 (example.com)  ──── [인증서 제출] ────→  사용자의 브라우저
                   "내가 진짜 example.com 서버야"   (신분증이 진짜인지·유효기간이 맞는지 검증)
```

### 깨달음
**인증서를 내미는 쪽은 항상 서버, 검사하는 쪽은 브라우저**다. "서버가 → 브라우저에게 → 자신이 진짜 해당 도메인의 서버임을 증명"으로 화살표 방향을 고정한다.

## 2. SNI에서 "IP 하나에 여러 도메인"을 반대로 기억함

### 처음 생각 (오답)
- SNI를 묻는 단답형에 설명할 때 들었던 비유 단어인 `리셉션`을 그대로 적었다.
- 서술형에서는 "한 도메인에 여러 IP가 묶여 있을 때 원하는 IP 주소를 찾기 위해"라고 도메인과 IP의 관계를 반대로 적었다.

### 원리
클라우드나 웹 호스팅에서는 비용과 IPv4 부족 문제 때문에 **서버(IP 주소) 한 대 안에 여러 회사의 웹사이트(도메인)를 함께 입주**시킨다(가상 호스팅).

```text
┌──────── 빌딩 1채 (IP: 203.0.113.5) ────────┐
│  - shop.example.com (쇼핑몰 인증서)         │
│  - blog.example.com (블로그 인증서)         │
└────────────────────────────────────────────┘
```
클라이언트가 TLS 핸드셰이크를 시작할 때(`Client Hello`), HTTP 요청(`Host:` 헤더)은 아직 암호화 전이라 보낼 수 없다. 그래서 핸드셰이크 첫마디에 **SNI(Server Name Indication)** 로 "저 `shop.example.com`에 왔어요"라고 사이트 이름을 먼저 알려주어야 서버가 쇼핑몰 인증서를 꺼내 줄 수 있다.

### 깨달음
"한 도메인에 여러 IP"가 아니라 **"하나의 IP에 여러 도메인"** 일 때 서버가 **맞는 인증서를 고르게 해주는 기술**이 **SNI**다.

## 3. 웹 캐시와 DNS 캐시, 쿠키의 용어 혼동

### 처음 생각 (오답)
- ETag를 설명할 때 "웹 사이트의 유효기간인 `TTL`이 끝나면 물어본다"라고 DNS 용어를 섞어 썼다.
- 객관식에서 ETag의 목적을 `① 콘텐츠의 길이를 알려 주는 값`으로 골랐고, 캐시 검증 헤더 짝(`ETag - If-None-Match`)을 몰랐다.
- `F5`와 `Ctrl + F5`의 차이를 "쿠키를 활용하느냐 / 세션까지 새로고침하느냐"라고 적었다.

### 원리
세 가지는 저장하는 대상과 헤더 이름이 완전히 다르다.

| 구분 | 저장하는 것 | 유효기간 / 검증 헤더 | 새로고침과 관계 |
|---|---|---|---|
| **DNS 캐시** | 도메인 → **IP 주소** | **TTL** (초 단위) | 무관 (`ipconfig /flushdns`) |
| **웹 캐시** | 이미지·CSS·JS **파일 사본** | **Cache-Control (`max-age`)**, 버전 검증은 **`ETag` ↔ `If-None-Match`** | **F5**(캐시 활용·재검증) vs **Ctrl+F5**(캐시 무시) |
| **쿠키 / 세션** | **로그인 상태·식별 번호표** | `Set-Cookie` ↔ `Cookie` | 새로고침해도 풀리지 않음 |

콘텐츠의 길이를 알려주는 헤더는 `Content-Length`이고, `ETag`는 파일의 **버전 식별자(번호표)** 다.

### 깨달음
유효기간은 **DNS = TTL, 웹 캐시 = Cache-Control**, 파일 버전 확인 짝은 **`ETag`(서버가 준 번호표) ↔ `If-None-Match`(브라우저가 물어볼 때 쓰는 헤더)**, 그리고 `F5 / Ctrl+F5`가 다루는 것은 쿠키·세션이 아니라 **웹 캐시**다.

## 4. QUIC의 특징 3가지("빠·독·이") 누락과 ABR 혼동

### 처음 생각 (오답)
- "HTTP/3에서 Wi-Fi가 LTE로 바뀌어도 연결이 끊기지 않는 이유"에 `UDP를 사용해서 ABR을 이용한 전송` 또는 `재접속 시 RTT가 0이라서`라고 다른 개념을 가져다 붙였다.
- 백지 서술형에서 QUIC의 특징을 쓸 때 `독립 스트림` 하나만 쓰고 나머지 두 개를 세 번 연속 빠뜨렸다.
- "HTTP/3는 UDP를 쓰니까 데이터가 빠져도 복구가 안 된다"는 OX 문제에 판단(틀리다)을 쓰지 않고 "선택에 따라 버릴지 결정한다"고 오답을 적었다.

### 원리
1. **ABR vs 연결 ID**: ABR은 유튜브 같은 영상 스트리밍에서 속도에 맞춰 **화질을 바꾸는 기술**이고, Wi-Fi → LTE 전환 시 IP가 바뀌어도 연결을 유지하는 것은 QUIC의 **연결 ID(Connection ID, 연결 마이그레이션)** 덕분이다.
2. **UDP 위지만 신뢰성 보장**: UDP 자체에는 재전송이 없지만, **QUIC이 UDP 위에서 스트림별 재전송과 혼잡 제어를 직접 구현**하므로 빠진 데이터는 모두 복구된다.
3. **QUIC의 3대 특징 ("빠·독·이")**:
   - **빠(빠른 연결)**: TLS 1.3 통합으로 **1-RTT**(재접속 **0-RTT**) 연결
   - **독(독립 스트림)**: 한 스트림에서 손실이 나도 다른 스트림은 멈추지 않음 (TCP HOL 해결)
   - **이(이동해도 유지)**: **연결 ID**로 식별해 IP가 바뀌어도 연결 유지

### 깨달음
HTTP/3(QUIC) 서술형이 나오면 시험지 구석에 **"빠(1-RTT) · 독(독립 스트림) · 이(연결 ID)"** 세 글자부터 적어 놓고 세 문단을 채운다.

## 5. 디피-헬만에서 비공개 값을 `초기값`이라고 적음

### 처음 생각 (오답)
디피-헬만 키 교환에서 끝까지 상대에게 보내지 않는 값을 두 번 연속 `초기 키값 / 초기값`이라고 적었고, $2^3 \bmod 11$을 계산할 때 나머지로 나올 수 없는 `11`을 적었다.

### 원리
- 초기 기준값인 $g=2, p=11$은 처음부터 **모두에게 공개된 값**이다.
- 각자 몰래 고른 **개인키($a, b$)** 와 최종 계산된 **공유 비밀키**는 네트워크로 절대 보내지 않는다. 네트워크로 오가는 것은 계산 결과인 **공개키($A, B$)** 뿐이다.
- $p=11$로 나눈 나머지는 항상 `0 ~ 10` 사이여야 하며, 나누는 수보다 작은 수($2^3 = 8 < 11$)는 몫이 0이고 **나머지가 자기 자신(`8`) 그대로**다.

### 깨달음
보내지 않는 값은 초기값이 아니라 **개인키(와 공유 비밀키)** 이며, $N \bmod p$에서 $N < p$이면 나머지는 $N$ 그대로다.

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| 인증서 = 브라우저가 서버에 본인 증명 | 서버가 브라우저에게 진짜 서버임을 증명 (서버 → 브라우저) |
| SNI = 한 도메인에 여러 IP 구분 | 하나의 IP에 여러 도메인이 있을 때 맞는 인증서 선택 |
| ETag = 콘텐츠 길이 / F5 = 쿠키 새로고침 | ETag = 캐시 버전 번호표(`If-None-Match`와 짝) / F5 = 웹 캐시 재검증 |
| Wi-Fi→LTE 연결 유지 = ABR / 0-RTT | 연결 ID(Connection ID)를 통한 연결 마이그레이션 |
| 디피-헬만에서 안 보내는 값 = 초기값 | 초기 기준값($g, p$)과 공개키는 공개, 안 보내는 건 **개인키** |
