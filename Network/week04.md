## 1. 웹 캐시(Web Cache)와 조건부 요청(ETag)

한 번 받은 이미지·CSS 등의 리소스를 브라우저에 보관해 두고 재사용하여 지연을 줄인다.

```text
[1] 첫 요청 및 응답
브라우저 ── GET /logo.png ─────────────────────────→ 서버
        ←─ 200 OK
           Cache-Control: max-age=3600   ("1시간 동안은 묻지 말고 캐시 써")
           ETag: "v7"                    ("이 파일 버전 번호표는 v7이야")
           (본문: 로고 이미지 데이터)

[2] 유효기간(max-age) 만료 후 재검증
브라우저 ── GET /logo.png
           If-None-Match: "v7" ────────────────────→ ("저 v7 갖고 있는데 바뀌었나요?")
        ←─ (안 바뀜) 304 Not Modified (본문 없음!)   ("그대로니 캐시 사본 쓰세요")
        ←─ (바뀜)    200 OK + ETag: "v8" + 새 본문   ("v8로 바뀌었으니 새로 받으세요")
```

- **Cache-Control**: 캐시 가능 여부와 유효기간(`max-age`)을 지정해 **성능**(트래픽·지연 감소)과 **최신성**(오래된 사본 방지, `no-store`/`no-cache`)의 균형을 맞춘다.
- **F5(새로고침)** vs **Ctrl + F5(강력 새로고침)**: `F5`는 캐시를 활용해 서버에 재검증(`304`)을 요청하고, `Ctrl + F5`는 **캐시를 완전히 무시**하고 모든 리소스를 서버에서 새로(`200`) 받는다.

## 2. HTTPS와 TLS 핸드셰이크
- **HTTPS** = `HTTP` + **`TLS`** (과거 명칭 SSL). 포트 번호는 **443**.
- **TLS의 3대 보안 제공**: **기밀성**(암호화) · **무결성**(변조 방지) · **인증**(서버 신원 확인)
- **TLS 3요소**:
  1. **암호 스위트(Cipher Suite)**: 사용할 암호 기술(키 교환·인증·암호화·무결성)의 세트 메뉴
  2. **키(Key)**: 실제 데이터를 잠그고(암호화) 여는(복호화) 비밀 숫자 값
  3. **인증서(Certificate)**: **서버가 브라우저에게** 자신이 진짜 해당 도메인의 서버임을 증명하는 디지털 신분증

### TLS 핸드셰이크 과정 (TCP 연결 직후, HTTP 요청 직전)
```text
① Client Hello (브라우저 → 서버) : 지원 TLS 버전, 암호 스위트 목록, 키 교환 그룹, SNI 제안
② Server Hello (서버 → 브라우저) : 사용할 TLS 버전과 암호 스위트 1개 선택
③ Certificate  (서버 → 브라우저) : 서버 인증서 전달 (브라우저가 유효기간 notBefore/notAfter 및 체인 검증)
④ 키 교환 (디피-헬만 등)         : 양측이 개인키는 숨긴 채 공개키만 교환해 동일한 공유 비밀키 생성
⑤ 암호화 통신 시작               : 이후 모든 HTTP 요청·응답을 공유키로 암호화하여 전송
```

- **인증서 항목**: **Subject**(대표 도메인 이름), **SAN(Subject Alternative Name)**(인증서 하나로 보장하는 여러 도메인 목록), **notBefore / notAfter**(유효기간 시작일 / 만료일 — PC 시스템 시계가 틀리면 여기서 경고 발생)
- **SNI (Server Name Indication)**: **하나의 IP 주소에서 여러 도메인(웹사이트)을 운영**할 때, `Client Hello` 첫마디에 접속할 도메인 이름을 평문으로 먼저 알려주어 서버가 알맞은 인증서를 꺼내게 하는 기술

## 3. 디피-헬만(Diffie-Hellman) 키 교환 원리

키 자체를 네트워크로 보내지 않고도 양쪽이 똑같은 공유 비밀키를 만들어내는 방법이다. (지수법칙 $(g^a)^b = (g^b)^a = g^{ab} \bmod p$ 활용)

| 구분 | 클라이언트 ($a = 3$) | 서버 ($b = 4$) | 공개 여부 |
|---|---|---|---|
| 공개 기준값 | $g = 2,\; p = 11$ | $g = 2,\; p = 11$ | 모두 공개 |
| **개인키 선택** | $a = 3$ | $b = 4$ | **절대 전송 안 함 (비공개)** |
| **공개키 계산·교환** | $A = 2^3 \bmod 11 = \mathbf{8}$ 전송 → | ← $B = 2^4 \bmod 11 = \mathbf{5}$ 전송 | 네트워크로 교환 (노출됨) |
| **공유 비밀키 계산** | $B^a \bmod 11 = 5^3 \bmod 11 = \mathbf{4}$ | $A^b \bmod 11 = 8^4 \bmod 11 = \mathbf{4}$ | **둘 다 4로 일치 (비공개)** |

## 4. HTTP 버전별 차이 (HTTP/1.1 → HTTP/2 → HTTP/3)

| 구분 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| **전송 계층 기반** | TCP | TCP | **QUIC (UDP 기반)** |
| **데이터 형식** | 텍스트 기반 | **이진(바이너리) 프레이밍** | 이진 프레이밍 |
| **동시 처리** | 한 줄로 순차 처리 (`keep-alive`로 연결만 재사용) | **스트림 다중화** (1개 TCP 연결에서 여러 요청 동시 섞어 전송) | **독립 스트림 다중화** |
| **헤더 처리** | 매 요청마다 같은 헤더 반복 전송 | **헤더 압축 (HPACK)** | 헤더 압축 (QPACK) |
| **HOL Blocking** | HTTP 단계 + TCP 단계 모두 발생 | HTTP HOL은 해결했으나 **TCP의 순서 보장 때문에 TCP HOL 잔존** | 손실 난 스트림만 대기 → **스트림 단위 HOL 완화** |
| **연결 설정** | TCP 3-way + TLS 별도 (2~3 RTT) | TCP 3-way + TLS 별도 | **TLS 1.3을 QUIC에 통합 (1-RTT, 재접속 0-RTT)** |
| **네트워크 전환** | IP 바뀌면 연결 끊김 | IP 바뀌면 연결 끊김 | **연결 ID(Connection ID)로 연결 마이그레이션 지원** |

- **QUIC의 핵심 특징 3가지 ("빠·독·이")**:
  1. **빠른 연결**: TCP 핸드셰이크와 TLS 1.3 암호화 협상을 하나로 합쳐 **1-RTT**(재접속 **0-RTT**) 만에 연결한다.
  2. **독립 스트림 멀티플렉싱**: 스트림별로 순서와 재전송을 독립 처리하여, 한 스트림에서 패킷이 유실돼도 **다른 스트림은 멈추지 않고 계속 진행**된다(체감 지연 감소).
  3. **연결 마이그레이션(경로 이동)**: 연결을 IP·포트가 아닌 고유한 **연결 ID**로 식별하여, Wi-Fi에서 LTE로 바뀌어 IP가 달라져도 연결이 끊기지 않고 유지된다.

## 5. 이메일 프로토콜과 스팸 방지(SPF · DKIM · DMARC)

```text
[발신자 메일 앱] ──(1) SMTP(587)──→ [발신 메일 서버] ──(2) SMTP(25)──→ [수신 메일 서버] ──(3) IMAP(993)/POP3(995)──→ [수신자 메일 앱]
                                         │
                              (DNS에 수신 도메인의 MX 레코드 조회)
```

| 프로토콜 | 방향 | 특징 |
|---|---|---|
| **SMTP** | 발신 · 서버 간 전달 | 메일을 **밀어 넣을 때(보낼 때)** 사용하는 프로토콜 |
| **POP3** | 수신함에서 꺼내기 | 메일을 내 기기로 **다운로드한 뒤 서버에서 삭제** (여러 기기 동기화 불가) |
| **IMAP** | 수신함 열람·동기화 | 메일을 **서버에 그대로 두고** 여러 기기(폰·PC)에서 동일하게 동기화 |

- **발신자 위장(스푸핑) 방지 3요소** (모두 도메인의 **DNS TXT 레코드**에 등록):
  - **SPF**: 메일을 보낸 서버의 IP가 해당 도메인이 **허가한 공식 발송 서버 명단**에 있는지 확인
  - **DKIM**: 메일에 찍힌 **전자서명**으로 발신 도메인 진위와 전송 중 **본문 변조 여부**를 검증
  - **DMARC**: SPF와 DKIM 검증이 실패했을 때 **어떻게 처리할지(거부·격리 등) 정한 정책**

## 6. ABR과 웹 접속 트러블슈팅 4단계
- **ABR (Adaptive Bitrate)**: 영상을 몇 초 단위의 **세그먼트(조각)** 로 자르고 여러 화질(240p~1080p)로 **CDN**에 저장해 둔 뒤, 네트워크 속도와 버퍼 상태에 맞춰 조각마다 화질을 자동 선택해 끊김을 막는 기술
- **웹 접속 트러블슈팅 4단계 관문**:
  ```text
  ① DNS (nslookup, 캐시 삭제, DoH) ──→ ② 연결·포트 (ping, tracert, 443 포트 개방, 방화벽)
  ──→ ③ TLS (시계, 인증서 체인, 보안 장비) ──→ ④ HTTP (404 경로, 3xx 루프, 500 서버 로그)
  ```
