## 1. 백지 서술형에서 흐름 제어와 혼잡 제어의 정의를 반대로 적음

### 처음 생각 (오답)
서술형 백지 테스트에서 `혼잡 제어 = 남은 버퍼의 양을 보고 수신 측에서 제어`, `흐름 제어 = 라우터에 연결된 기기들의 혼잡도를 보고 송신 측에서 결정`이라고 **이름표를 서로 뒤바꿔** 적었다.

### 원리
단어의 뜻 그대로 연결하면 절대 뒤집히지 않는다.

```text
흐름(Flow) 제어       : 물(데이터)을 받는 그릇(수신 버퍼)이 넘치지 않게 수위 조절  → 수신 측 기준 (rwnd, r = receiver)
혼잡(Congestion) 제어 : 교통 혼잡! 고속도로(라우터·네트워크)가 막히지 않게 조절  → 네트워크 기준 (cwnd, c = congestion)
```

### 깨달음
**"교통 혼잡 = 도로(라우터) 이야기 = `cwnd`"**, **"흐름 = 받는 그릇(수신 버퍼) 이야기 = `rwnd`"**.

## 2. `rwnd`와 `cwnd`가 동시에 있을 때 실제 전송량 결정

### 처음 생각 (오답)
- "`rwnd = 8`, `cwnd = 3`일 때 실제로 한 번에 보낼 수 있는 양은?"이라는 질문에 "뭘 기준으로 봐야 하는지 모르겠다"고 답했다.
- 다음 점검에서는 "실제 한 번에 보내는 양은 무엇으로 정해지나?"에 `rwnd(버퍼의 남은 공간)` 하나만 적었다.

### 원리
```text
[보내는 쪽] ──── 도로: 트럭 3대까지만 통과 가능 (cwnd = 3) ────→ [창고: 8칸 비어 있음 (rwnd = 8)]
```
창고에 8칸이 비어 있다고 트럭 8대를 한꺼번에 보내면 도로에서 5대가 막혀 사고(혼잡 손실)가 난다. 반대로 도로가 8차선(`cwnd = 8`)이어도 창고가 3칸(`rwnd = 3`)뿐이면 3대만 보내야 창고가 넘치지 않는다.
가족 나들이에서 **가장 느린 꼬마의 걸음걸이에 맞춰야** 모두가 함께 갈 수 있는 것과 같다.

### 깨달음
실제 전송량은 `rwnd` 하나만이 아니라 항상 **`rwnd`와 `cwnd` 중 더 작은 값($\min(\text{rwnd}, \text{cwnd})$)** 으로 정해진다.

## 3. 4-way 핸드셰이크를 3단계(`ACK+FIN` 합침)로 그림

### 처음 생각 (오답)
연결 종료 과정을 백지에 그릴 때 `FIN → ← ACK+FIN → FIN+ACK`처럼 3-way 핸드셰이크와 똑같이 서버의 `ACK`와 `FIN`을 한 줄로 합쳐서 3단계로 그렸다.

### 원리
- **연결 시작(3-way)** 때는 서버가 연결 요청을 수락(`ACK`)함과 동시에 자기 연결 요청(`SYN`)을 보내는 데 아무런 거리낌이 없어 **`SYN+ACK` 한 번에** 보낸다.
- **연결 종료(4-way)** 때는 클라이언트가 "할 말 끝났어(`FIN`)"라고 해도, **서버 쪽에서는 아직 보내던 데이터가 남아 있을 수 있다.** 그래서 일단 "알았어(`ACK`)"만 먼저 보내고, 남은 데이터를 다 보낸 뒤에야 "나도 끝났어(`FIN`)"를 **따로** 보낸다.

```text
① FIN  ──→        (클라이언트: 난 다 보냈어)
       ←── ② ACK  (서버: 알았어, 근데 난 아직 보낼 데이터 남았어)
       ←── ③ FIN  (서버: 다 보냈다! 나도 이제 끊을게)   ★ ②와 ③이 분리되어 4단계!
④ ACK  ──→        (클라이언트: 알았어, TIME-WAIT 시작)
```

### 깨달음
종료가 4-way인 이유는 **"남은 데이터를 마저 보내야 해서 ② `ACK`와 ③ `FIN`을 합치지 못하고 따로 보내기 때문"** 이다.

## 4. TIME-WAIT 이유에서 `포트 재사용` 키워드 누락과 임시 포트 변경 이유

### 처음 생각 (오답)
- TIME-WAIT가 필요한 이유를 쓸 때 "아직 다 수신받지 못한 패킷을 기다림, 오래된 패킷 소멸"이라고만 쓰고 핵심 키워드인 **`포트 재사용`** 을 두 번 연속 빠뜨렸다.
- "브라우저를 재실행하면 임시 포트가 바뀌는 이유"에 "캐시를 새로 받기 때문"이라고 답했다.

### 원리
1. **TIME-WAIT와 포트 재사용**: TIME-WAIT는 덜 받은 데이터를 마저 받으려는 시간이 아니다(데이터는 `FIN` 전에 이미 다 받았다). 연결이 끝난 직후 **똑같은 포트 번호를 재사용**해 새 연결을 바로 열었을 때, 네트워크에 늦게 떠돌던 **이전 연결의 오래된 패킷**이 새 연결에 섞여 들어가는 사고를 막기 위해 포트를 잠시 묶어두는 시간이다.
2. **임시 포트 변경**: 임시 포트는 캐시와 전혀 무관하다. 클라이언트가 새 연결을 맺을 때마다 **OS가 비어 있는 동적 포트(49152~65535) 중에서 그때그때 새로 뽑아 할당**하기 때문에 바뀐다.

### 깨달음
TIME-WAIT 서술형은 **"오래된 패킷 + 포트 재사용 시 새 연결 방해 방지"** 가 한 세트이고, 임시 포트는 **연결할 때마다 OS가 동적으로 새로 뽑아주어서** 바뀐다.

## 5. `netstat -ano`의 PID를 원격 서버의 프로세스로 착각할 뻔함

### 처음 생각 (오답)
`netstat -ano`에서 확인할 수 있는 3가지 항목과 `PID`의 의미를 몰라 빈칸으로 두었다.

### 원리
```text
 프로토콜   로컬 주소:포트          원격 주소:포트          상태          PID
  TCP     192.168.0.10:52410   142.250.196.238:443   ESTABLISHED   15204
```
내 컴퓨터에서 실행한 명령어이므로, 상대방(구글 서버) 안에서 몇 번 프로그램이 도는지는 알 방법도 없고 보안상 알려주지도 않는다. 맨 끝의 `PID(Process ID)`는 **내 컴퓨터(로컬)에서 이 소켓 연결을 만든 프로그램(예: `chrome.exe`)의 번호**다.

### 깨달음
`netstat -ano`의 3요소는 **주소:포트(로컬·원격) · 연결 상태 · 로컬 PID**다.

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| 흐름 제어 = 라우터, 혼잡 제어 = 수신 버퍼 | 흐름 제어 = 수신 버퍼(`rwnd`), 혼잡 제어 = 네트워크·라우터(`cwnd`) |
| 실제 전송량 = `rwnd`만 봄 | $\min(\text{rwnd}, \text{cwnd})$ — 두 값 중 더 작은 값 |
| 종료할 때도 `ACK+FIN`을 합쳐 3번에 끝냄 | 보낼 데이터가 남을 수 있어 `ACK`와 `FIN`을 따로 보냄 (4-way) |
| 임시 포트가 바뀌는 이유 = 캐시 때문 | 연결 때마다 OS가 동적 포트 범위에서 새로 할당하기 때문 |
| `netstat -ano`의 PID = 서버 프로세스 | 내 컴퓨터(로컬)에서 연결을 연 프로세스의 ID |
