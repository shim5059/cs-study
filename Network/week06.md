## 1. TCP 헤더 구조 (기본 20바이트, 옵션 포함 시 최대 60바이트)

```text
 0                   16                   32 (비트)
┌────────────────────┬────────────────────┐
│    출발지 포트      │    목적지 포트      │  ← 어느 프로세스 → 어느 프로세스
├────────────────────┴────────────────────┤
│         순서 번호 (Sequence Number)      │  ← 이 세그먼트 첫 바이트의 번호 (순서 보장)
├─────────────────────────────────────────┤
│       확인 응답 번호 (ACK Number)         │  ← 다음에 받고 싶은 바이트 번호 (누적 ACK, 도착 보장)
├──────┬─────┬───────────────┬────────────┤
│헤더   │예약 │ 플래그         │ 윈도우 크기  │  ← 플래그(SYN·ACK·FIN·RST·PSH) / 수신 윈도우(rwnd)
│길이   │     │ (6~8 bits)    │ (Window)   │
├──────┴─────┴───────┬───────┴────────────┤
│       체크섬        │    긴급 포인터      │  ← 헤더+데이터 오류 검출
├────────────────────┴────────────────────┤
│        옵션 (MSS, SACK, Window Scale)    │
└─────────────────────────────────────────┘
```
- **주요 플래그**: `SYN`(연결 요청, 순서 번호 동기화), `ACK`(확인 응답 유효), `FIN`(연결 정상 종료), `RST`(연결 강제 초기화), `PSH`(버퍼에 모으지 않고 즉시 응용 프로그램에 전달)

## 2. 연결 설정 (3-way Handshake)과 종료 (4-way Handshake)

### 1) 3-way Handshake (연결 시작)
```text
클라이언트                                         서버
    │ ── ① SYN (Seq=x) ─────────────────────────→ │  연결 요청
    │ ←──────────────── ② SYN+ACK (Seq=y, Ack=x+1) │  요청 수락(ACK) + 서버도 연결 요청(SYN)
    │ ── ③ ACK (Ack=y+1) ───────────────────────→ │  서버 요청 확인 → 연결 완료(ESTABLISHED)
```
- 양방향 모두 "내 신호가 상대에게 닿고 상대 신호도 나에게 닿는다"는 것을 확인하고 초기 순서 번호(ISN)를 동기화하기 위해 3단계가 필요하다.
- **SYN만 반복되고 SYN+ACK가 안 올 때 원인**: ① 서버가 꺼져 있거나 해당 포트를 열어두지 않음(Listening 아님) ② 중간 방화벽·보안 정책 차단

### 2) 4-way Handshake (연결 종료)와 TIME-WAIT
```text
먼저 끊는 쪽                                      상대방
    │ ── ① FIN ─────────────────────────────────→ │  "보낼 데이터 다 보냈어, 끊을게"
    │ ←─────────────────────────────────── ② ACK ─ │  "알았어 (잠깐, 난 아직 보낼 게 남았어)"
    │            ... 남은 데이터 마저 전송 ...       │
    │ ←─────────────────────────────────── ③ FIN ─ │  "나도 다 보냈어, 끊을게"
    │ ── ④ ACK ─────────────────────────────────→ │  "알았어" → 상대방 연결 종료
    │ ⏳ TIME-WAIT (잠시 대기 후 최종 종료)          │
```
- **왜 4단계인가**: 연결할 때와 달리 종료 시점에는 상대방이 **아직 보낼 데이터가 남아 있을 수 있어서** 일단 `ACK`만 먼저 보내고, 남은 전송을 마친 뒤 `FIN`을 **따로** 보내기 때문이다.
- **TIME-WAIT가 필요한 이유**: 네트워크를 떠돌던 **오래된 패킷**이 뒤늦게 도착했을 때, 같은 **포트를 재사용**하여 새로 맺어진 연결에 섞여 들어가 방해하는 것을 막고, 마지막 `ACK`가 유실됐을 때 `FIN` 재전송에 응답하기 위해 잠시 기다린다.

## 3. 데이터 전송(Seq · 누적 ACK)과 재전송 2가지

- **순서 번호(Seq)**: 송신 측이 붙이는 번호로, 세그먼트 데이터의 **첫 바이트가 전체에서 몇 번째 바이트부터인지** 나타낸다.
- **확인 응답 번호(ACK)**: 수신 측이 붙이는 번호로, **"그 앞까지는 모두 잘 받았으니 다음에는 이 번호부터 보내달라"** 는 뜻이다(**누적 ACK**).
  - 예: 100바이트씩 `Seq=100(100~199)`, `Seq=200(200~299)`를 모두 받으면 **`ACK=300`** 응답.
- **슬라이딩 윈도우(Sliding Window)**: `ACK`를 하나씩 기다리지 않고 윈도우 크기만큼 연속으로 보낸 뒤, `ACK`가 오는 만큼 창을 옆으로 밀어 다음 데이터를 전송해 효율을 높이는 방식.

### 손실 복구: 빠른 재전송 vs 타임아웃 재전송

```text
[빠른 재전송: Seq=200 손실 시]
Seq=100 ──→ 도착 (ACK=200)
Seq=200 ──✗ 손실!
Seq=300 ──→ 도착 (200이 비어 있으므로 여전히 ACK=200 전송 → 중복 ACK ①)
Seq=400 ──→ 도착 (여전히 ACK=200 전송 → 중복 ACK ②)
Seq=500 ──→ 도착 (여전히 ACK=200 전송 → 중복 ACK ③)
  ⇒ 같은 ACK가 3번 중복 수신되면 타이머(RTO)를 기다리지 않고 즉시 Seq=200 재전송!
Seq=200 ──→ 재전송 도착 ⇒ 이미 받아둔 300~599까지 합쳐 한 번에 ACK=600 전송!
```

| 구분 | 빠른 재전송 (Fast Retransmit) | 타임아웃 재전송 (Timeout Retransmit) |
|---|---|---|
| **감지 신호** | 동일한 ACK가 **3번 중복 수신(3중 중복 ACK)** | **RTT**를 측정해 계산한 **RTO** 시간 안에 아무 응답 없음 |
| **상황 판단** | 뒤 패킷들은 도착 중 → **일부 패킷만 손실** | 패킷이 아예 못 지나감 → **심한 네트워크 혼잡** |
| **동작** | 타이머 만료를 기다리지 않고 **즉시 재전송** | RTO 만료 후 재전송 (대기 시간 2배 증가) |

## 4. 흐름 제어(rwnd) vs 혼잡 제어(cwnd)

| 구분 | 흐름 제어 (Flow Control) | 혼잡 제어 (Congestion Control) |
|---|---|---|
| **조절 기준** | **수신 측**이 처리할 수 있는 여유 공간(**수신 버퍼**) | **중간 네트워크(라우터)** 가 감당할 수 있는 상태 |
| **윈도우 값** | **`rwnd`** (Receive Window, 수신 측이 헤더에 적어 알려줌) | **`cwnd`** (Congestion Window, 송신 측이 스스로 추정) |
| **실제 전송량** | $\text{실제 전송 가능량} = \min(\text{rwnd}, \text{cwnd})$ (**둘 중 더 작은 값**에 맞춤) |

- **혼잡 제어의 `cwnd` 변화**:
  - **느린 시작(Slow Start)**: `cwnd = 1`에서 출발해 **RTT(왕복)마다 2배씩 지수 증가**(1 → 2 → 4 → 8…)하다가 임계점부터 1씩 선형 증가(혼잡 회피)
  - **3중 중복 ACK 발생 시**: 일부 손실로 보고 `cwnd`를 **절반($1/2$)** 으로 줄인 뒤 선형 증가
  - **타임아웃(RTO) 발생 시**: 심한 혼잡으로 보고 `cwnd`를 **`1`로 확 줄인 뒤** 다시 느린 시작

## 5. 전송 계층 진단 도구와 '느림'의 분해
- **`Test-NetConnection -ComputerName [IP] -Port 443`**: 특정 IP와 포트로 **TCP 3-way 핸드셰이크가 성립하는지** 확인 (`TcpTestSucceeded: True / False`)
- **`netstat -ano`**: 현재 PC의 ① **로컬·원격 주소:포트**, ② **연결 상태**(`ESTABLISHED`, `LISTENING`, `TIME_WAIT`), ③ **로컬 프로세스 ID(PID)** 확인
- **Wireshark 표시 필터**: `tcp.port == 8000` (TCP 출발지/목적지 포트가 8000인 패킷), `udp.port == 53` (DNS 트래픽)
- **'느림'의 3가지 원인 분해**:
  1. **손실**: 무선 간섭 등으로 패킷이 유실되어 **재전송**하느라 느림
  2. **혼잡**: 라우터에 트래픽이 몰려 **큐잉 지연**이 커지고 **`cwnd`가 줄어들어** 느림
  3. **수신자 병목**: 수신 측 CPU·버퍼가 바빠 **`rwnd`가 줄어들어** 못 보내서 느림
