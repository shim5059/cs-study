## 1. CIDR `/24`의 숫자를 IP 주소의 `1`의 개수로 착각함

### 처음 생각 (오답)
`192.168.0.15/24`를 보고 "`192.168.0.15`를 2진수로 바꾸면 `1`이 8개뿐인데 왜 뒤에 `/24`가 붙는가? 그리고 `255.255.255.0`은 IP 주소가 아닌가?"라고 헷갈렸다. 또한 `10.0.5.0/24`를 보고 뒤에 `/24`가 붙어 있으니 옛 클래스 기준으로도 `C 클래스`라고 답했다.

### 원리
1. **`/n`의 정체**: `/24`는 앞의 IP 주소(`192.168.0.15`)에 들어 있는 1의 개수가 아니라, 별도의 자(尺)인 **서브넷 마스크(`255.255.255.0`)에 연속으로 들어 있는 `1`의 개수**다.
   ```text
   IP 주소      : 192.168.0.15  = 11000000.10101000.00000000.00001111
   서브넷 마스크 : /24           = 11111111.11111111.11111111.00000000 (255.255.255.0)
                                  └──── 앞 24비트가 동네 이름 ────┘└ 호스트 ┘
   ```
2. **클래스 vs CIDR**: 옛날 클래스(A·B·C)는 `/n`과 상관없이 오직 **첫 번째 옥텟 숫자**(`10`은 `1~126`이므로 **A 클래스**)로만 결정된다. `10.0.5.0/24`는 "원래 A 클래스 대역인 주소를 CIDR을 사용해 `/24`(254대 크기)로 잘라서 쓰고 있다"는 뜻이다.

### 깨달음
`/n`은 **서브넷 마스크의 1의 개수(네트워크 비트 길이)** 이고, 옛 클래스(A·B·C)를 물으면 `/n`을 보지 말고 **맨 앞 숫자(1~126 A / 128~191 B / 192~223 C)** 만 본다.

## 2. 서브넷 계산에서 나온 5가지 연쇄 오답

### 처음 생각 (오답)
- `/24`에서 기기에 줄 수 있는 주소를 구할 때 호스트 비트를 $32-24=8$이 아니라 24를 그대로 써서 $2^{24}$라고 계산했다.
- `192.168.10.100/26` 문제를 풀 때:
  1. 세 번째 옥텟 `10`을 `/26`의 6으로 바꿔 `192.168.6.100`이라고 적었다.
  2. 브로드캐스트 주소를 묻는 칸에 마스크인 `255.255.255.0`을 적었다.
  3. 마지막 숫자가 `.100`이 아니라 `.190`이면 동네 크기도 64에서 128로 커진다고 생각했다.
- `/25`의 주소 개수와 기기 수를 쓸 때 `주소 개수 126개, 기기 수 128개`로 둘을 거꾸로 적었다.

### 원리
1. **동네 크기는 오직 `/n`만 결정한다**: 호스트 비트 $k = 32 - n$이고, 한 서브넷의 전체 주소 개수는 **$B = 2^{(32-n)}$** 이다. IP 주소 뒷자리가 `.10`이든 `.100`이든 `.190`이든 `/26`이면 동네 크기는 무조건 $2^{(32-26)} = 2^6 = \mathbf{64}$다.
2. **앞 세 칸 복사**: `/24 ~ /30`에서는 앞 세 옥텟(24비트)의 마스크가 `255.255.255`이므로 앞 세 칸(`192.168.10`)은 절대 바뀌지 않고 그대로 복사된다.
3. **네트워크 주소 vs 브로드캐스트 주소 vs 기기 수**:
   ```text
   192.168.10.100/26  →  크기 64씩 끊으면 [0~63], [64~127], [128~191], [192~255]
   100이 속한 구간은 [64 ~ 127]
   - 구간 맨 앞 (.64)  = 네트워크 주소 (동네 표지판)
   - 구간 맨 뒤 (.127) = 브로드캐스트 주소 (동네 방송 스피커)
   - 전체 주소 개수 = 64개, 실제 기기 수 = 양 끝 2개를 뺀 62대 (기기 수가 항상 2 작다!)
   ```

### 깨달음
- 서브넷 크기는 $B = 2^{(32-n)}$으로 먼저 구한다.
- **전체 주소 개수($B$)가 항상 더 큰 수**이고, **기기 수($B-2$)는 양 끝(네트워크·브로드캐스트 주소)을 빼서 항상 2만큼 더 작은 수**다.

## 3. 기본 게이트웨이의 주어 방향과 용어 혼동

### 처음 생각 (오답)
- 수업 메모에 `라우터가 처음 만나는 것 = 기본 게이트웨이`라고 주어를 반대로 적었다.
- 단답형에서 "다른 네트워크로 나가는 출구 역할의 이름"을 물었을 때 3번 연속 `모름` 또는 `공유기`라고 적었다.

### 원리
- 라우터가 처음 만나는 것이 아니라, **내 컴퓨터(호스트)가 다른 서브넷으로 나갈 때 처음 만나는 라우터**가 **기본 게이트웨이(Default Gateway)** 다.
- `공유기`는 가정에서 그 역할을 수행하는 기계 이름이고, 네트워크 공식 역할 명칭은 **기본 게이트웨이**다.

### 깨달음
"내 PC가 다른 네트워크로 나갈 때 패킷을 가장 먼저 맡기는 동네 출입문 역할 = **기본 게이트웨이**".

## 4. ARP와 RARP, DNS의 역할 혼동

### 처음 생각 (오답)
"같은 LAN에서 IP 주소로 MAC 주소를 알아내는 프로토콜"을 물었을 때 1차 점검에서는 `RARP (MAC으로 IP는 ARP)`라고 정반대로 적었고, 다음 점검에서는 `DNS`라고 적었다.

### 원리
```text
[보낼 때 캡슐화 순서: 위(3계층) → 아래(2계층)]
1. 도메인 이름만 앎  ──(DNS)──→  목적지 IP 주소를 알아냄 (3계층 패킷 완성)
2. 다음 홉 IP는 앎   ──(ARP)──→  다음 홉 MAC 주소를 알아냄 (2계층 프레임 완성)
```
패킷을 포장할 때 위층(IP)은 이미 알고 아래층(MAC)을 모르기 때문에, 매번 필요한 정방향 프로토콜인 **ARP**가 **`IP → MAC`** 이다. 반대로 부팅 시 내 MAC만 알고 내 IP를 물어보는 역방향(**R**everse)이 **RARP**(`MAC → IP`)다.

### 깨달음
- **DNS**: `도메인 이름 → IP 주소`
- **ARP**: `IP 주소 → MAC 주소` (캡슐화 정방향)
- **RARP**: `MAC 주소 → IP 주소` (**R**everse, 역방향)

## 5. IP의 TTL과 DNS의 TTL 혼동

### 처음 생각 (오답)
- 수업 필기에서 IP의 TTL이 0이 될 때를 `표기`라고 잘못 적었다.
- DNS 캐시 유효기간을 묻는 질문에 `TLS`라고 답했고, 웹 캐시 설명에 `TTL`을 가져다 썼다.

### 원리
같은 약어(`TTL, Time To Live`)지만 계층에 따라 단위와 뜻이 완전히 다르다.

| 구분 | 계층 | 단위 | 의미와 만료 시 동작 |
|---|---|---|---|
| **IP의 TTL** | 3계층(네트워크) | **홉 수 (라우터 개수)** | 라우터를 지날 때마다 1씩 감소, **`0`이 되면 패킷 폐기(버림)** 후 ICMP 시간 초과 전송 |
| **DNS의 TTL** | 7계층(응용) | **초 (시간)** | DNS 응답(IP 주소)을 **캐시에 보관해도 되는 유효기간**, 만료 시 캐시에서 삭제 후 재질의 |

### 깨달음
IP의 TTL은 **라우터 홉 수(0 되면 폐기)** 이고, DNS의 TTL은 **캐시 유효 시간(초)** 이다. (TLS는 HTTPS 암호화 프로토콜이다.)

## 정리

| 착각 | 바로잡은 규칙 |
|---|---|
| `/24` = IP 주소의 1의 개수 / C 클래스 | `/24` = 서브넷 마스크의 1의 개수, 클래스는 첫 옥텟 숫자로만 판단 |
| `/25` 주소 개수 126, 기기 수 128 | 전체 주소 개수가 $2^7=128$, 기기 수는 2를 뺀 $126$ (기기 수가 항상 2 작음) |
| 라우터가 처음 만나는 것 = 공유기 | **호스트(내 PC)** 가 밖으로 나갈 때 처음 만나는 라우터 = **기본 게이트웨이** |
| IP → MAC 변환 = RARP / DNS | 도메인→IP는 **DNS**, IP→MAC은 **ARP**, MAC→IP는 **RARP** |
| IP TTL 0 되면 표기 / DNS 유효기간 = TLS | IP TTL 0 되면 **폐기(버림)** / DNS 캐시 유효기간 = **TTL(초)** |
