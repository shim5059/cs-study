# 8주차 · 패킷트레이서로 ping 한 번 따라가기 (ARP, PDU, STP·CDP·DTP)

> 헷갈렸던 부분과 해결 과정: [week08-deep-dive.md](week08-deep-dive.md)

> 4장 실습 · 시험 강조: **패킷트레이서 실습 출제 가능**, ping 한 번의 전체 흐름(ARP → ICMP), PDU 계층별 정보 읽기

## 1. 같은 서브넷 ping 한 번에 일어나는 일

PC0(`192.168.10.10`)이 PC2(`192.168.10.11`)에게 `ping`을 보내는 상황.

1. PC0이 ICMP Echo Request를 만든다. 목적지가 같은 서브넷이므로 게이트웨이 없이 직접 보내기로 결정한다.
2. 상대 **MAC을 모르므로 ARP 요청을 브로드캐스트**한다. (목적지 MAC `FFFF.FFFF.FFFF`, "192.168.10.11 가진 기계 누구냐?")
3. 해당 PC만 **ARP 응답을 유니캐스트**로 보내 자기 MAC을 알려준다.
4. PC0은 받은 MAC으로 프레임을 만들어 **ICMP Echo Request/Reply를 4번 왕복**한다.

| 질문 | 답 |
|---|---|
| 왜 ping보다 ARP가 먼저인가 | 선 위로 보내려면 이더넷 프레임에 **목적지 MAC**이 필요한데, 알고 있는 건 IP뿐이라서 |
| 요청은 왜 브로드캐스트인가 | 상대 MAC을 **모르니** 한 명을 콕 집을 수 없어서 LAN 전체에 뿌림 |
| 응답은 왜 유니캐스트인가 | 요청 프레임에 보낸 쪽 MAC이 들어 있어 **이미 누군지 알기** 때문 |

- 한 줄 요약: **상대 MAC을 모를 땐 전체에게, 알면 그 한 명에게.**
- 응답이 돌아올 때 **TTL이 128 그대로**면 라우터를 한 번도 안 거친 것이다. (라우터 1홉마다 1 감소)
- 패킷트레이서에서 첫 ping만 `Request timed out`이 뜨고 나머지가 성공하는 경우가 많은데, 첫 번째가 ARP 과정에 시간을 쓰기 때문이다.

### ARP 테이블 (`arp -a`)

ARP로 알아낸 결과는 **IP와 MAC의 짝**으로 캐시에 저장된다. 그래서 이어지는 ping은 ARP를 다시 하지 않는다.

```text
Internet Address    Physical Address     Type
192.168.10.11       0001.4321.aaaa       dynamic   ← ARP로 자동 학습, 시간 지나면 삭제
```

## 2. PDU Information으로 계층별 캡슐화 읽기

- Simulation 모드에서 진행 중인 패킷(봉투)을 클릭하면 PDU Information 창이 열린다.
  - **Outbound PDU Details**: 보낼 때 포장한 모습 (캡슐화)
  - **Inbound PDU Details**: 받아서 푸는 모습 (역캡슐화)
- 편지 → 봉투 → 택배 상자처럼 안쪽부터 포장하고, 받는 쪽은 바깥부터 푼다.

| 계층 | 들어 있는 정보 | ping 예시 |
|---|---|---|
| 3계층 ICMP | 메시지 종류 | Echo Request |
| 3계층 IP | 출발지/목적지 IP, TTL | `192.168.10.10 → .11`, TTL 128 |
| 2계층 Ethernet | 출발지/목적지 MAC | PC0 MAC → PC2 MAC (ARP 요청이면 `FFFF.FFFF.FFFF`) |

### 라우터를 거칠 때 바뀌는 것

| 항목 | 변화 |
|---|---|
| 출발지/목적지 **IP** | **끝까지 그대로** ("누가 누구에게") — 예외: NAT |
| 출발지/목적지 **MAC** | **홉(구간)마다 바뀜** ("이번 한 칸에서 누가 누구에게") |
| **TTL** | 라우터를 지날 때마다 1 감소 |

```text
PC0 → R1 구간 : IP 10.10 → 20.10 | MAC PC0 → R1 왼쪽 포트
R1 → PC3 구간 : IP 10.10 → 20.10 | MAC R1 오른쪽 포트 → PC3
```

- 다른 서브넷으로 보낼 때 PC0은 **최종 목적지가 아니라 게이트웨이의 MAC을 ARP로 묻는다.** ARP 요청은 브로드캐스트라 **같은 LAN 안에서만** 닿고, 라우터는 브로드캐스트를 넘기지 않기(브로드캐스트 도메인의 경계) 때문이다.
- "다른 LAN인지"는 자기 IP와 서브넷 마스크로 목적지가 같은 네트워크인지 비교해서 판단한다. (7주차 서브넷 계산)

## 3. ping과 상관없이 배경에서 도는 프로토콜

| 이름 | 하는 일 | 비유 |
|---|---|---|
| **STP** | 스위치 이중 연결 시 **루프**가 생기지 않게 일부 포트를 막음 | 순환 도로 한 곳을 막아 둠 |
| **CDP** | 시스코 장비끼리 "나 누구, 어느 포트"를 알려 주는 이웃 소개 | 옆집과 명함 교환 |
| **DTP** | 케이블 양쪽이 트렁크/액세스를 협상 | "이 선에 VLAN 여러 개 실을까?" |

### 주황불 → 초록불 (약 30초)

- **STP** 때문이다. 포트가 막 켜졌을 때 열면 루프가 생기는지 아직 모르므로, **주황(검사 중)** 상태에서 확인한 뒤 **초록(전달 시작)** 이 된다. (listening 15초 + learning 15초)
- 루프가 위험한 이유: 브로드캐스트가 스위치끼리 계속 돌며 **브로드캐스트 스톰**이 된다. IP 패킷은 TTL로 결국 죽지만 **이더넷 프레임에는 TTL이 없어서** 저절로 멈추지 않는다.
- 한 줄 요약: **주황은 루프 검사 중, 초록은 검사 통과.**

## 4. IP·게이트웨이 설정과 `ipconfig`

| 항목 | 의미 | 예 |
|---|---|---|
| IPv4 주소 | 내 주소 | `192.168.10.10` |
| 서브넷 마스크 | 어디까지가 같은 LAN인지 | `255.255.255.0` |
| 기본 게이트웨이 | LAN 밖으로 나가는 출구(라우터) | `192.168.10.1` |

- 패킷트레이서 PC Config에서 **IPv6가 아니라 IPv4 칸**에 입력한다.
- `ipconfig`: 위 세 값 확인 / `ipconfig /all`: MAC 주소까지 확인
- 고정 IP는 Static, 자동 할당은 DHCP. (집 공유기는 DHCP, 학교 실습실은 고정)

### 게이트웨이를 비워 두면

| 목적지 | 결과 | 이유 |
|---|---|---|
| 같은 서브넷 | 정상 | 게이트웨이를 쓸 일이 없음, ARP로 상대 MAC만 알면 됨 |
| 다른 서브넷 | **`Destination host unreachable`** | 나갈 출구를 몰라 패킷이 PC 밖으로 나가지도 못함 |

### 오류 문구 구분

| 문구 | 의미 | 예 |
|---|---|---|
| `Destination host unreachable` | **보내지도 못함** (경로·출구 없음) | 게이트웨이 미설정, 라우터에 경로 없음 |
| `Request timed out` | **보냈는데 답이 안 옴** | VLAN이 달라 ARP 응답 없음, 돌아오는 경로 없음 |
